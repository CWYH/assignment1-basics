# TinyStories BPE 多语言性能对比

**修订说明：下表保留的是初版实现结果。后续发现并修正 C# 预分词中的实现问题后，完整训练三轮中位耗时降为 8.30 秒（默认 Workstation GC），使用 Server GC 则为 7.58 秒；新结果与词表、合并规则的验证详见 [C# 专项分析](../bpe_csharp_investigation/REPORT.md)。因此，“C# 最慢”不再适用于修正后的默认实现。**

在同一台机器上，对完整 TinyStoriesV2-GPT4 训练集运行三轮测试，结果为：
**本次实现中 C++ 最快，Java 次之，Python 再次，C# 的端到端训练最慢。**
四个版本的最终词表（包括 ID）和全部 9,743 条有序合并规则完全一致。

## 实验条件

- 输入：`data/TinyStoriesV2-GPT4-train.txt`，2,227,753,162 字节。
- SHA-256：`6418d412de72888f52b5142c761ac21a582f7d1166f0bfbdb5f03ccfdec90443`。
- 最大词表：10,000，包含 256 个字节 token 和 `<|endoftext|>`。
- CPU：Intel Core i7-12700，20 个逻辑处理器；约 31.82 GiB RAM；Windows 11。
- 每个版本使用 8 个预分词工作单元：Python 使用进程，其余版本使用线程。
- 每个版本独立运行三次，每次新建进程；各版本串行测量，轮换顺序。
- Python 3.13.5 / regex 2026.3.32；GCC 14.1.0 / PCRE2 10.46 JIT，Release `-O3`；
  .NET SDK 8.0.404 / runtime 8.0.11，Release；Amazon Corretto 11.0.24，`-Xms64m -Xmx2g`。

## 测量结果

所有时间单位为秒，每一列分别取三轮的中位数，因而各阶段中位数之和不一定严格等于总时间中位数。

| 版本 | 预分词与汇总 | 初始化索引和堆 | 合并 | 训练总耗时 | 进程总耗时 | 峰值 RSS（MiB） | 相对 Python 加速比 |
|---|---:|---:|---:|---:|---:|---:|---:|
| C++ | 5.23 | 0.11 | 0.89 | **6.22** | 6.31 | **536.1** | **8.12×** |
| Java | 14.74 | 0.16 | 0.70 | **15.90** | 16.17 | 1455.6 | **3.18×** |
| Python | 48.13 | 0.21 | 2.21 | 50.52 | 50.67 | 1115.8 | 1.00× |
| C# | 72.57 | 0.28 | 0.78 | 73.69 | 73.88 | 2382.7 | 0.69× |

三轮训练总耗时分别为：

| 版本 | 第 1 轮 | 第 2 轮 | 第 3 轮 |
|---|---:|---:|---:|
| Python | 55.10 | 50.52 | 45.08 |
| C++ | 6.22 | 6.02 | 6.80 |
| C# | 75.19 | 73.69 | 73.51 |
| Java | 15.90 | 15.21 | 16.07 |

训练计时包含读取文件、预分词、统计、初始化和 BPE 合并，不含进程启动和输出序列化；
进程总耗时包含启动、训练和序列化。本次没有开启 `cProfile`，因此不应将这里的阶段时间
与此前带 profiler 的 50.62 秒直接混用；此前无 profiler 的 43.32 秒是另一次单轮运行。

内存是每 20 ms 采样一次的主进程及子进程 RSS 合计峰值，表中取三轮峰值的中位数。
这个指标可能遗漏短暂尖峰，也可能重复计算共享页面；托管运行时的 GC 堆策略也会影响它。

## 如何解释差异

四个版本都使用频率加权的去重预分词片段、相邻对到片段的倒排索引、惰性删除堆和增量统计，
并按照字节对的字典序处理频次相同的情况。各版本的完整训练都以预分词阶段为主要开销。

三个移植版本的合并阶段均比 Python 快，但 C# 的预分词耗时抵消了这一收益，说明只优化
BPE 合并循环不足以保证端到端训练更快。本次没有单独对 C# 的内部热点做 profiler，
因此不能仅凭阶段计时断言是正则引擎、字符串分配或 GC 中哪一项造成了全部差异。

这比较的是当前几份实现及其运行时，不是“语言本身”的统一排名：C++ 使用 PCRE2 JIT，
C# 使用 .NET 编译正则，Java 使用 Unicode 模式的 Pattern，Python 使用 regex；
它们的数据结构、内存管理和 Unicode 数据版本也不同。文件缓存未清空，JVM/.NET 未做
专门的进程内预热，因此结果体现新进程执行完整训练的成本，而非稳定态微基准。

这些独立训练器面向当前 TinyStories 实验，固定使用一个 `<|endoftext|>` 特殊 token；
不替代 Python 的通用接口，也不包含推理阶段的编码和解码。不同正则引擎对任意 Unicode
输入的行为并非全部相同，验证结论仅覆盖实际训练集和边界样例。

## 验证与复现

- 英文参考语料、5 MB TinyStories 样本，以及中文、emoji、空白、重叠字节对和特殊 token 边界样例，四种实现全部一致。
- 12 次完整训练的词表和有序合并列表均与既有 Python 结果逐项一致。
- 原有及并行 Python 训练测试 7 项全部通过；Python 工具脚本通过 Ruff 检查。
- 三个原生版本通过自动构建脚本成功构建。

从仓库根目录执行：

```powershell
uv run python benchmarks/bpe_native/build.py
uv run python benchmarks/bpe_native/run_benchmarks.py --runs 3 --workers 8
```

源代码与构建说明见 [README](../../benchmarks/bpe_native/README.md)。
